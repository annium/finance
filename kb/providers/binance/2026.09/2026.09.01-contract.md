# Contract drift check — binance, 2026-09-01

First documentation pass. It turns the manifest from an inventory into a baseline — and it found one
change that has almost certainly been breaking the USDⓈ-M futures connector since April.

Written against the snapshot in `2026.09.01-docs/`, not the live sites. Spot is pinned at commit
`a005775`; futures has no repository, so its anchor is the fetch date.

## Blocking

### The futures WebSocket base URLs were decommissioned on 2026-04-23

`2026.09.01-docs/usd-futures/websocket-market-streams_Important-WebSocket-Change-Notice.md`

Binance split the futures WebSocket into three base URLs — `/public` for high-frequency public feeds,
`/market` for regular market data, `/private` for user data — and states plainly:

> Legacy URLs will remain available until 2026-04-23, after which they will be permanently
> decommissioned. […] After the upgrade, any connections not migrated will ONLY be able to receive
> data from `wss://fstream.binance.com/public`. Channels under `/market` and `/private` will stop
> pushing data.

**That date passed four months ago.** We are on the legacy URLs in both places:

| what | ours | documented now |
|---|---|---|
| market stream | `wss://fstream.binance.com` + `/stream` — `UsdFutures/Internal/Shared/Endpoints.cs:32-33`, `UsdFutures/Internal/Market/Profiles/MarketConfigProfile.cs:39` | `wss://fstream.binance.com/public/stream?streams=…` for `@bookTicker`, which the notice lists under **Public** |
| user stream | `{WsApi}/ws/{listenKey}` → `wss://fstream.binance.com/ws/<key>` — `Base/Internal/User/Services/UserStream.cs:112`, `UsdFutures/Internal/User/Profiles/UserConfigProfile.cs:48` | `wss://fstream.binance.com/private/ws/<key>` — confirmed twice, by the notice and by `user-data-streams.md` |

**What this costs us.** The user stream carries every order and account update; on a decommissioned
URL it delivers nothing, so a futures user connector connects, reports itself healthy, and never sees
a fill. The market stream carries `@bookTicker`, which the notice assigns to `/public` — the one
category legacy connections may still receive — so tickers may still arrive while account data does
not. That asymmetry is the worst possible shape: the connector looks alive.

Note what this would have done to the exchange validation we were about to run. Stage 6d would have
placed a real order and then waited forever for an update that cannot arrive, and every instinct would
have pointed at our own sync cycle — the code we spent twenty-two rounds hardening. **This is the
finding that justifies the whole arrangement:** it was unreachable by any test we could write and
invisible to any amount of reading our own code.

**Remediation** belongs to layer 5 (endpoints and configuration), and is not applied here.

## Changed

| what | was | is now | ours |
|---|---|---|---|
| `GET /fapi/v1/userTrades` history | 6 months | **3 months** (2026-08-26) | our 7-day windows are unaffected; the manifest's reach was wrong |
| `GET /fapi/v1/allOrders` `symbol` | mandatory | **optional** (2026-08-25) | we always send it — still valid, contract widened |
| spot signature payload | sign the query string | **percent-encode before signing**; otherwise `-1022 INVALID_SIGNATURE` (2026-01-15) | see below |

On the signature change: we sign `req.Uri.Query`
(`Base/Shared/HttpExtensions/HttpRequestSignatureExtensions.cs:38`), which is the composed `Uri`'s
query and therefore already percent-encoded. We are compliant — **by construction rather than by
intent**, and nothing pins it. The golden-value test uses `symbol=LTCBTC&side=BUY&…`, which contains
nothing that needs encoding, so it would pass equally with a non-encoding implementation. The exposure
today is small because every parameter we send is alphanumeric; it stops being small the first time
one is not.

## New — available, unused

- **`GET /fapi/v3/account`** returns only symbols with a position or an open order, unlike `v2`. We use
  `v2` (`UsdFutures/Internal/User/UserProvider.cs:68`) and should keep it: the test fixture's one-way
  position-mode precondition depends on `v2` returning a row per symbol regardless. **Recorded so that
  a future migration to `v3` knows it breaks that precondition** — which is exactly the kind of thing
  that gets discovered the expensive way.
- **`symbolStatus: CANCEL_ONLY`** is a new exchange-information value (from 2026-07-07). Our converter
  admits only `TRADING`, so such a symbol is dropped entirely. That is almost certainly right — you
  cannot open a position on it — but it is now a decision rather than an accident, and it is recorded
  as one.
- `ACCOUNT_UPDATE` gained field `S` on `FUNDING_FEE` events; `PUT /fapi/v1/order` gained optional
  `modifyId`; `allOrders` and `userTrades` gained response fields. All additive, all ignored by our
  converters, none requiring action.

## Resolved — an assumption that was flagged and is now settled

The manifest carried `[UNVERIFIED]`: the listen-key resolver's own doc comment promises "periodic PUT
keep-alive confirmations" while the code only ever POSTs, and a prior review reported this as a defect.

The documentation settles it in our favour:

> Doing a `POST` on an account with an active `listenKey` will return the currently active `listenKey`
> and extend its validity for 60 minutes.

**The code is correct; the comment is wrong.** Worth recording as method as much as outcome — the
defect report was plausible, and acting on it would have introduced a bug into working code. It was
held as unverified precisely so that a documentation pass, not a plausible argument, would decide it.

## Found on the second pass — states nobody mapped

Neither is drift: Binance documents these and always did. We simply never wrote them down, which is
what the documentation axis is for.

**Symbol status is not a two-value question.** Spot documents `TRADING`, `END_OF_DAY`, `HALT`, `BREAK`
and `CANCEL_ONLY`; futures documents ten values including `TRADING_HALT` and `TRADING_CANCEL_ONLY`. Our
converters admit `TRADING` alone, so **every other state drops the instrument entirely**. A halted
symbol becomes indistinguishable from one the exchange never listed — defensible when deciding whether
to open a position, wrong for a connector already holding one, which will watch the instrument vanish
rather than learn it was halted.

**Spot documents `PENDING_NEW` and we do not map it.** An order in an order list sits there until its
working order fills; our lookup would find nothing. Dead in practice — the spot user path throws long
before — but a hole rather than a decision. Binance separately notes `PENDING_CANCEL` is "currently
unused", so our folding of that one costs nothing and proves nothing.

## Unchanged

Every spot response field our converters read, `confirmed` at tier 1 against `rest-api.md` — including
`cummulativeQuoteQty` with Binance's own spelling, and `isMaker`, which is `maker` on futures. Both
venues' order-type and order-status wire strings, checked against their documented lists. Every filter
type name and field, including that spot documents both `MIN_NOTIONAL` and `NOTIONAL` while futures
documents only the former.

Signing algorithm and what is signed; the API-key header; `recvWindow` semantics; the weight header's
name and shape (`X-MBX-USED-WEIGHT-(intervalNum)(intervalLetter)`, which our case-insensitive
`x-mbx-used-weight-1m` match still satisfies); the numeric error codes we map; every filter type name
and field; every order-type, order-status and position-side wire string.

The divergences the manifest records between spot and futures — six order-type strings, the notional
filter's type and field names, `isMaker` versus `maker` — all still stand as recorded. None has moved,
which is worth knowing: they are the entries most likely to move next.

## Unresolved — one, and it is cheap to settle

**`POST /fapi/v1/order` may not return `avgPrice`, and our converter reads it.** The catalog lists
`avgPrice` on the query-order response and not on the new-order response;
`UsdFutures/.../InitOrderResponseConverter.cs:123` reads it either way. If the listing is right, a
newly placed order comes back with an executed price of zero — which for a market order is the number
the caller most wants.

Not reported as a finding, because the reading is tier 3: a model's answer about a page, not the page.
Either the response really omits the field, or the reading is incomplete — and a tier-3 source cannot
decide between those on its own.

It settles itself at the first live order placed in step 5, which is where the fact would be observed
directly. Until then it stands as recorded doubt, not as a defect and not as an all-clear.

## Undocumented

None newly identified. Separating genuinely undocumented dependencies from merely unverified ones
needs the stream-event schemas, which remain unretrievable — see the gap below.

## What the request side now rests on

The official Postman collections (`binance/binance-api-postman`, pinned at `bf7c418`) cover all 95
futures requests including every endpoint this module calls, with full parameter lists. Tier 1,
diffable, and a better source for request shape than any rendered page. They carry no response
examples at all, so they close the request side and nothing more.

Two parameters they document that we do not send, both optional and both new: `priceMatch` and
`modifyId` on `PUT /fapi/v1/order`.

## Still a gap

The nested payloads of the user-data-stream events — `ORDER_TRADE_UPDATE`'s order object,
`ACCOUNT_UPDATE`'s balance and position entries — render from a schema source no available technique
reached. Roughly twenty short field names in the manifest depend on them and remain unverified against
their own page.

**The Binance MCP server was considered for this and rejected.** It is not a documentation server: it
is an account-connected agent reached by OAuth, and Binance's own page says "never paste the MCP
endpoint into an AI chat and ask it to install the server". Wrong instrument, and one the vendor
explicitly warns against installing this way.

## What our tests would notice — the verification census

Run over every manifest entry against the suites, because a drift check that only asks what the
provider says answers half the question. The other half is what of ours would notice.

**The blocking finding is watched by nothing.** The user-stream URI — the entry that stops the trading
validation — is not pinned and not even gated: no test anywhere opens the user-data websocket. The
most consequential fact in the manifest sits in code no test touches. That is why review found it and
nothing else could have, and it is the sharpest argument in this report for keeping both axes rather
than one.

**Two tests cannot fail, and both fail the same way** — the input chosen cannot exercise the property:

1. The signing golden value, whose query has no character needing the percent-encoding Binance began
   requiring in January.
2. The history paging tests, which request one day of history while claiming to protect a seven-day
   chunking window and a three-month cap. Even with the gate open they can only confirm the call did
   not error.

**Five components have no test file at all** — `WebSocketService`, `ListenKeyResolver`,
`HttpRequestSignatureExtensions`, `HttpRequestLogExtensions`, and the filter converters. The first two
carry the connection lifecycle of every stream this module runs.

**Two claims of mine were wrong**, and the census is what caught them. Enumerations are not pinned as a
category: only values that appear in some fixture are covered, and on the read side most order types
and all but two order statuses are untested — the write side is pinned per type, which is what I saw
and over-generalised. Request parameters went the other way: the futures query processor is pinned
offline, better than I claimed.

**Where the exposure actually is.** The untested bucket's centre of mass is not the exotic paths but
the **constants** — production rate-limit ceilings, `recvWindow`, the water mark, the precision
heuristics. The values easiest to copy wrong and hardest to notice.

## Does anything block running against the exchange?

**Yes — stage 6d, and probably 6b.**

Fix the futures WebSocket base URLs first. Running the trading suite against a user stream that cannot
deliver would burn a real order and produce a diagnosis pointing at the wrong code.

Stages 6a (signing, server time) and 6c (authenticated reads over REST) are unaffected — neither uses
a WebSocket — and can proceed as planned.
